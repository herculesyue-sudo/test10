# 合規詞庫掃描器

發布前的關卡。掃描文案是否命中已知的違規用語規則，輸出位置、依據條文與改寫建議。

## 掃什麼、不掃什麼

| 目標 | 掃不掃 | 為什麼 |
|---|---|---|
| **對外文案**（社交貼文、廣告、網站、單張、影片字幕稿） | ✅ **必掃**，`--warn-as-block` | 這是規則存在的原因 |
| **提案文件**（`proposals/`） | ✅ 掃 | 會交到第三方手上 |
| **最終設計稿的文字**（抽出成 .txt 再掃） | ✅ **必掃**，加 `--no-suppress` | 見下方警告 |
| **內部策略文件**（`docs/`） | ❌ 不必掃 | 這些文件為了說明「不可以講什麼」而**引用**受禁詞語，必然大量命中。硬要掃只會製造雜訊，最後你會開始無視警告——那時工具就死了 |

## 用法

```bash
# 掃描對外文案（預設 all 市場，最嚴格）
python3 compliance/check.py drafts/post-001.md

# 指定市場
python3 compliance/check.py drafts/*.md --market hk

# 快速檢查一句話
echo "食完血糖降咗" | python3 compliance/check.py -

# 最終發布關卡：warn 也當作不通過
python3 compliance/check.py drafts/post-001.md --warn-as-block

# 稽核：忽略所有豁免，看看到底豁免了什麼
python3 compliance/check.py proposals/*.md --no-suppress

# 給自動化流程
python3 compliance/check.py drafts/post-001.md --json
```

## 退出碼

| 碼 | 意思 |
|---|---|
| 0 | 無 block 級發現 |
| 1 | 有 block 級發現 → **不得發布** |
| 2 | 用法或檔案錯誤 |

## 豁免機制

掃描器是關鍵字比對，**分不出「聲稱」和「否認聲稱」**。
「不會作任何療效聲稱」這句話會命中 `TREAT-CLAIM`，雖然它正正是在說不會這樣做。

所以有兩種豁免。**兩種都必須寫理由——沒有理由的豁免不生效**，
這樣每個豁免都可以被追溯和審核。

### 行內豁免

```markdown
<!-- compliance-ok: TREAT-CLAIM 否定句，說明不可使用此聲稱 -->
我們不會作任何療效聲稱。

我們不會作任何療效聲稱。 <!-- compliance-ok: TREAT-CLAIM 否定句 -->
```

- 附在**內容行末** → 只豁免該行
- **獨立成一行**的註釋 → 只豁免下一行（同 `eslint-disable-next-line`）
- 多條規則用逗號分隔；`*` 豁免該行所有規則

### 檔案層級豁免

寫在檔案開頭 15 行內：

```markdown
<!-- compliance-file-ok: TREAT-CLAIM,HK-231-DISEASE 內部指引，引用受禁詞語以說明不可使用 -->
```

**檔案層級刻意不接受 `*`** —— 必須逐條列明規則代號。
一個檔案層級的萬用豁免等於把掃描器關掉，那就沒有意義了。

### ⚠️ 最終稿必須用 `--no-suppress` 再掃一次

提案與範本文件裡的豁免，是因為那些檔案同時包含**對外文案**和**內部說明**。
當你把一頁提案的文字抽出來做成實際的 A4 設計稿時，
那份稿裡不應該再有任何需要豁免的東西。

```bash
# 把最終設計稿的文字存成 final-copy.txt，然後：
python3 compliance/check.py final-copy.txt --market hk --no-suppress --warn-as-block
```

**這一步必須通過，零 BLOCK、零豁免。**

## 規則庫

規則在 [rules.json](rules.json)。每條規則：

| 欄位 | 說明 |
|---|---|
| `id` | 規則代號，出現在報告與豁免宣告中 |
| `markets` | 適用市場：`hk` `cn` `us` |
| `severity` | `block`（不得發布）／`warn`（需人工判斷） |
| `pattern` | 正則表達式，大小寫不敏感 |
| `satisfied_by` | 選填。若整份文件含此內容則該規則不觸發（例如已附免責聲明） |
| `reason` | 法律依據 |
| `suggestion` | 改寫方向 |

新增規則直接改 JSON，不需改程式。改完跑一次現有草稿確認沒有大量誤報。

## 接入發布流程

```
AI 生成草稿
   ↓
check.py --market <目標>   ← 自動，不通過就打回
   ↓
指定人工簽核（記錄簽核人與日期）
   ↓
最終稿 check.py --no-suppress --warn-as-block
   ↓
人手發布
```

小紅書內容用 `--market cn`；香港 FB／IG 用 `--market hk`；跨市場素材用預設 `all`。

## 限制（請認真看待）

- 這是**關鍵字比對，不是語意理解**。改寫後的違規句（比喻、諧音、圖片內文字）照樣通過。
- 監管機構看的是**整體印象**，不是逐字對照。一篇每個詞都合格、
  但整體讀落去就係「呢隻嘢醫得好糖尿病」的貼文，一樣會出事。
  這就是為什麼 [內容審核簽核表](../templates/README.md#4--內容審核簽核表)
  裡「整體印象檢查」那一格才是真正的關卡。
- **掃描通過 ≠ 合規。** 它只代表沒有命中已知規則。人工簽核不可省。
- 圖片、影片內的文字與旁白不會被掃描，需另行人手檢查。
- 規則庫依據撰寫時的理解編寫，**須經執業律師覆核並定期更新**。
